# Workbench Command Sets Design

## Goal

Turn the current single Linux command workbench into a first-class Command Sets container. The desktop and embedded Terminal must enter the same browser. Linux remains a compiled, read-only system preset; users can create editable command sets stored under their own home directory.

## Navigation

Desktop:

```text
Workbench Files
Terminal
Command Sets
Settings
Exit Workbench
```

Command Sets:

```text
Linux Commands        [System] [Read-only]
<user sets...>         [Custom]
+ New Command Set
```

Opening Linux Commands preserves the current category -> task navigation and current Linux/CentOS profile overlay. Opening a user set shows its custom actions.

The browser has two exit modes:

- `COMMAND_MODE_EXECUTE`: desktop selection renders parameters and executes through the existing confirmation/safety pipeline.
- `COMMAND_MODE_INSERT`: Terminal selection renders parameters and inserts the command into the live shell input without sending Enter.

No separate flattened Terminal command palette remains.

## Command Set Model

Each set has an ID, bilingual-capable display name/description storage, source type, read-only flag, action array, and action count.

Sources:

- `COMMAND_SET_SYSTEM`: compiled Workbench preset; read-only and not deletable.
- `COMMAND_SET_USER`: user-owned `.wbc`; editable and deletable.
- `COMMAND_SET_PLUGIN`: reserved for future plugin sets; read-only by default, plugin lifecycle controls installation/removal.

The built-in Linux set wraps the current effective task catalogue (`Linux Core + selected distro overlay`) without copying the task data to disk.

## User Storage

User sets live at:

```text
~/.local/share/workbench/command-sets/
```

Constraints:

- directory mode `0700`
- files mode `0600`
- maximum 64 user command sets
- maximum 256 actions per user set
- write with temporary file + `fsync`/close + atomic `rename`
- malformed or unsupported files are ignored and never executed
- duplicate set IDs are rejected
- system IDs cannot be shadowed

The initial Workbench `.wbc` format is line-oriented and libc-only. Values use explicit escaping for backslash/newline/tab/equal-sign/control-sensitive bytes. The format records set metadata plus repeated action sections using the existing `Task`, `Risk`, `ArgKind`, and `{1}`..`{4}` semantics.

## User Action Editing

A user action supports:

- ID generated by Workbench
- name
- description
- keywords
- command template
- risk level
- up to four parameter definitions using existing `TaskArg`

Only placeholders actually present in the command template require argument metadata.

System command sets reject set rename/delete and action add/edit/delete at the model layer, even if UI code calls the mutation API accidentally.

## UI and Input

All Command Sets pages use the existing unified `UiEvent` layer and support keyboard-only and mouse-only operation. Text fields reuse `ui_input_dialog`, which means the existing optional virtual keyboard remains available.

User set page operations:

- Open/run selected action
- Search
- Properties
- Add action
- Edit selected action
- Delete selected action
- Edit set metadata
- Delete set
- Back

Linux system pages remain visually consistent with the existing category/task UI but show `[System] [Read-only]` at the Command Sets level.

## Safety

Custom actions do not bypass Workbench parameter quoting/validation or confirmation policy. Desktop execution uses the existing rendered-command and risk confirmation pipeline. Terminal insertion renders the same safe parameter substitutions but does not execute automatically.

The `.wbc` parser never evaluates content. It only constructs data objects. Commands execute only after explicit user selection.

## Release Criteria

- Generic Linux still exposes 374 effective system actions.
- CentOS profile still exposes 483 effective system actions with 110 overlay actions and one override.
- Linux system set is read-only in model and UI.
- User set and action CRUD survives reload.
- Keyboard-only CRUD PTY flow passes.
- Mouse-only CRUD PTY flow passes with virtual keyboard enabled.
- Desktop user action executes only after normal confirmation flow.
- Terminal system/user action inserts without auto-running.
- Existing Files, Settings, Profile, dual-input, Terminal, self-test, release-policy, and source-package tests pass.
- Build is warning-free with `-Wall -Wextra -Wpedantic`.
- Source tar remains source-only and rebuilds/tests successfully after extraction.
